## Context

仓库目前只有 OpenSpec 配置，没有既有应用、数据库或兼容负担。本变更建设一个需要登录、以定投计划为一级容器的 Web 应用：React 前端负责交互，Gin 后端提供 REST API，GORM 访问 MySQL。用户可以创建多个计划；每个计划拥有自己的定投目的地、配置、月度收支、计算快照、实际投入和统计。

新计划默认展示支付宝基金、A股、港美股、现金四个目的地，但它们只是可编辑模板。用户可以只保留部分默认项或增加其他目的地。核心约束是金额计算确定可复算、业务数据按用户与计划双重隔离、历史月份不因后来修改计划或目的地而被静默改写。

## Goals / Non-Goals

**Goals:**

- 提供“登录 → 计划列表/创建 → 计划详情 → 月度收支与计算 → 实际投入与统计”的清晰流程。
- 支持每个用户创建多个计划，每个计划维护一个或多个可配置定投目的地。
- 以 Gin 服务作为身份校验、计划归属校验、业务校验、定投计算和持久化的权威来源。
- 使用 GORM 和 MySQL 持久保存账号、计划及其子资源，并在数据库、Repository 和 API 三层强制用户隔离。
- 将金额、比例、取整和任意数量目的地分配实现为无副作用的 Go 领域函数并进行边界测试。
- 保存每次计算使用的计划与目的地快照，使历史数据可解释、可审计。

**Non-Goals:**

- 不提供第三方登录、密码找回、管理员角色或细粒度权限。
- 不导入微信、支付宝或其他平台账单，也不按消费用途分类。
- 不管理证券持仓、份额、价格、净值、收益率或汇率，不发起真实交易。
- “现金”在第一版只是一个可分配和记录实际金额的目的地，不管理银行账户余额或现金流转。
- 不在第一版提供预算预测、智能投顾或基于市场行情的动态调仓。

## Decisions

### 1. 采用 React + TypeScript 前端和 Gin + GORM 后端

前端使用 React、TypeScript 和 Vite。登录后首先进入计划列表；计划详情包含概览、计划设置、月度录入、历史和统计。前端通过统一的 typed API client 调用后端，服务端返回的数据是持久状态来源。

后端使用 Gin 处理路由、中间件和 JSON API，按 handler、application service、domain、repository 分层。GORM 实现 MySQL Repository，HTTP handler 不直接拼装数据库查询或实现计算公式。

### 2. 计划是所有定投业务数据的一级容器

关系层级为：

~~~text
User
 ├─ Expense Sources
 └─ Plans
     ├─ Destinations
     └─ Monthly Records
         ├─ Expense Snapshots
         └─ Destination Allocation Snapshots
~~~

支出来源由用户维护并可在不同计划中复用；每月的具体来源金额属于某个计划。计划、目的地、月度记录、实际投入、历史和统计 API 都通过 plan ID 嵌套访问。后端先使用“plan ID + 当前 user ID”确认计划归属，再访问任何子资源。

同一用户可以在不同计划中保存相同月份，数据库唯一约束为 (plan_id, month)。同一计划的同一月份只有一条记录。

### 3. 新计划使用可编辑默认模板，不强制固定目的地

创建计划时，系统加入支付宝基金、A股、港美股、现金四个默认目的地。默认目的地与用户新增目的地使用相同数据模型和行为，不存在不可删除或必须启用的特殊项。

用户可以新增、重命名、排序、启用或停用目的地。有效计划至少包含一个启用目的地，所有启用目的地的分配基点合计为 10,000；停用项不参与新月份计算。计划在满足这些条件前保持草稿状态，不能创建月度计算。

已经被历史快照引用的目的地只能停用/归档，不能物理删除；未被引用的目的地可以删除。重新启用目的地时，用户必须重新调整全部启用项比例到 100%。“现金”按普通目的地参与建议分配、实际金额登记和统计。

### 4. 后端是计算与校验的权威来源

浏览器可以即时显示支出合计等非权威预览，但最终计划校验、可定投基数、取整、目的地分配、执行状态和统计均由后端计算。保存月度记录和重新计算历史月份必须调用服务端应用服务，避免前后端规则漂移或客户端篡改结果。

所有 API 使用 /api/v1 前缀和统一 JSON 错误结构。未认证请求返回 401；访问不属于当前用户的计划或其子资源统一按资源不存在处理。

### 5. 使用用户名密码和可撤销的服务端会话

第一版允许用户使用唯一用户名和密码注册、登录和退出。密码使用 bcrypt 哈希，永不存储或返回明文。登录成功后生成高熵随机会话令牌，只把令牌哈希保存到 MySQL，把原始令牌放入 HttpOnly、SameSite=Lax、生产环境 Secure 的 Cookie。

认证中间件根据 Cookie 查找未过期会话并把 user ID 写入请求上下文。退出时撤销当前会话。生产环境前后端同源部署并校验 Origin，开发环境只允许配置的前端 Origin 携带凭据。

### 6. 每一层都显式传递用户与计划身份

受保护 handler 不接受客户端提交的 user ID，只使用认证上下文身份。所有计划查询使用“plan ID + user ID”；子资源 Repository 方法要求 user ID 和 plan ID，并通过关联或复合条件验证归属。更新和删除不得只按裸资源 ID 执行。

集成测试必须覆盖两个用户使用相同计划名称和月份、同一用户两个计划使用相同月份，以及尝试跨用户或跨计划访问子资源的场景。

### 7. 金额使用整数分、比例使用基点

API、Go 领域模型和 MySQL 均以整数“分”存储人民币金额，以 0 到 10,000 的整数基点存储比例，避免浮点误差。前端只负责元/分和百分比/基点的输入转换与格式化。

月度计算公式为：

~~~text
总支出 = Σ 当前计划本月各支出来源金额
收支结余 = 总收入 - 总支出
可定投基数 = max(收支结余 - 预留资金, 0)
建议定投总额原值 = 可定投基数 × 当月定投比例
建议定投总额 = 按取整单位向下取整(建议定投总额原值)
~~~

系统遍历该计划当前启用的 N 个目的地，按比例计算原始份额并按取整单位向下取整。剩余的完整单位按“小数余数最大优先”分配；余数相同时按目的地 sort_order，再按稳定 ID 打破平局。最终所有目的地金额非负、合计严格等于建议总额且不超过可定投基数。只有一个启用目的地时，其比例必须为 100%，并获得全部建议金额。

### 8. 使用关系模型保存可查询快照

核心表包括 users、sessions、plans、plan_destinations、expense_sources、monthly_records、monthly_expenses 和 monthly_destination_allocations。

- plans 保存用户归属、名称、草稿/启用/归档状态、默认定投比例、预留资金和取整单位。
- plan_destinations 保存计划归属、名称、启用状态、排序和当前分配比例。
- expense_sources 保存用户归属，可被该用户的多个计划复用。
- monthly_records 保存 plan ID、月份、收入、总支出、可定投基数、当月比例、预留资金快照、取整规则快照、建议总额、备注和版本号。
- monthly_expenses 保存来源 ID、来源名称快照和金额。
- monthly_destination_allocations 保存目的地 ID、名称快照、目标比例快照、建议金额和实际金额；目的地后续重命名或停用不改变历史。
- sessions 只保存令牌哈希、用户 ID、过期时间和撤销状态。

创建或重算月度记录时，在一个 MySQL 事务内写入主记录、支出明细和任意数量的目的地明细。实际投入更新也在事务内完成。金额列使用 BIGINT，比例使用整数列，计划月份建立唯一索引。

### 9. 月度记录始终从计划详情进入

用户必须先创建计划。计划有效后，计划详情提供“录入月份”入口；月度表单从该计划读取默认定投比例、预留资金、取整单位和当前启用目的地。月度覆盖只影响当前月份，不反向修改计划。

修改计划或目的地不会重算历史月份。用户主动编辑历史月份并确认重新计算时，后端继续使用该月已保存的目的地与比例快照，只更新现金流输入、计算中间值和建议金额，并完整保留各快照目的地的实际投入。新目的地结构只用于之后创建的新月份。

### 10. 支出按用户级“来源”建模，金额按计划记录

支出来源统一容纳微信、支付宝、美团、抖音、银行卡、交通等账单项。注册成功后为用户创建常用来源；用户可以新增、重命名、排序和停用来源。月度录入位于计划详情内，保存的是“该计划 + 该月份 + 来源”的金额快照。

系统无法判断多个计划是否重复录入同一份收入，也无法判断跨平台账单是否包含同一交易。因此计划页面提示月度收支只用于当前计划的分配计算；支出录入页提示同一笔交易在一个计划内只计入一个来源。

### 11. 历史与统计默认按计划聚合

计划详情的历史和仪表盘只聚合该计划的月度记录和目的地实际金额，展示每月建议/实际投入、累计实际投入、各目的地累计投入与占比，以及金额完成率。账户首页展示计划卡片与每个计划摘要，不把多个计划的收入和支出相加，避免重复录入导致误导。

金额完成率定义为“计划内累计实际投入 ÷ 计划内累计建议投入”；累计建议投入为零时返回不可用状态。

### 12. 使用版本化数据库迁移和环境配置

GORM 负责模型映射和查询，数据库结构通过按版本执行的迁移管理。配置来自环境变量，包括 MySQL DSN、会话密钥/有效期、允许的开发 Origin、Cookie 安全属性和服务端口；敏感配置不得进入仓库。

开发环境提供 MySQL 容器编排和示例环境文件，生产环境要求 HTTPS、独立数据库账号、最小权限和迁移前备份。

## Risks / Trade-offs

- [账号和财务数据提高了安全要求] → 使用 bcrypt、随机不透明会话、HttpOnly/Secure/SameSite Cookie、Origin 校验、登录限速和通用认证错误。
- [漏加用户或计划过滤可能导致越权] → user ID 不来自客户端，所有子资源方法要求 user ID 与 plan ID，并加入双用户、双计划隔离测试。
- [多个计划重复录入同一收入可能造成账户级重复统计] → 所有收入、支出和完成率默认按计划展示；账户首页不汇总跨计划收支。
- [目的地删除可能破坏历史] → 被历史引用的目的地只能归档，月度记录保存名称、比例、建议和实际金额快照。
- [动态目的地让取整分配更复杂] → 使用对任意 N 项都确定的最大余数法，并用 sort_order 与稳定 ID 打破平局。
- [计划修改可能让历史统计失真] → 只有显式重算才更新月度快照，普通计划编辑不追溯修改历史。
- [并发编辑同一计划或月份可能覆盖数据] → 计划和月度记录保存版本号，更新时执行乐观并发检查，冲突返回 409。
- [数据库迁移失败可能阻止部署] → 使用版本化迁移、启动前连通性检查、迁移前备份和向后兼容的扩展式变更。

## Migration Plan

这是全新应用，没有旧业务数据迁移。部署顺序为：准备 MySQL 和最小权限账号，执行版本化 schema migration，启动 Gin 服务并完成健康检查，再部署 React 静态资源。用户注册事务只创建账号、会话和常用支出来源；用户登录后自行创建第一个计划。

回滚应用版本前确认数据库迁移兼容性；非破坏性迁移保留旧列至少一个版本。发生迁移故障时停止新版本、恢复迁移前备份并回滚服务。
