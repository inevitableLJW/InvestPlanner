## Context

计划目前已经有 `draft`、`active`、`archived` 状态，但设置页通过同一份可编辑 `status` 数据保存，界面上的“保存计划设置”无法清晰表达是否会开始计划，也没有用于永久清理未开始草稿的入口。后端创建新计划时使用 100 分（1 元）作为默认取整单位，月度计算则以最大余数法把分项尾差分配给任意标的。此变更横跨 React 表单、Gin 服务、GORM 默认值、计划删除和领域计算，并且必须保持已有计划参数及历史月份快照稳定。

## Goals / Non-Goals

**Goals:**

- 新计划以 100 元为默认向下取整单位，用户仍可逐计划覆盖。
- 现金启用时稳定承接其他标的向下取整后的余额，分项合计始终等于建议总额。
- 把保存草稿和发布计划建模为显式写入意图，发布是计划开始的唯一入口。
- 允许用户永久删除当前为草稿且没有月度记录的未开始计划，同时保护已经开始或有历史的计划。
- 保持服务端为状态转换、校验和建议金额计算的权威来源。
- 保留已有计划设置和历史月度快照，不进行破坏性回填。

**Non-Goals:**

- 不为草稿增加多版本、自动保存、协作编辑或定时发布。
- 不允许永久删除运行中、已归档或包含任何月度记录的计划，也不在本次增加归档恢复页面。
- 不改变总建议金额公式、月度投入比例或历史快照重算规则。
- 不自动修改已有计划的取整单位，也不重算已保存月份。
- 不增加用户可配置的尾差目标；本次只识别规范名称“现金”。

## Decisions

### 1. 使用显式生命周期动作而非客户端可写状态

计划设置写入负载增加枚举动作（如 `save_draft`、`publish`），前端不再把可编辑 `status` 当作状态转换依据。服务端根据动作设置最终状态：`save_draft` 保存有效的基础字段与标的并强制为 `draft`；`publish` 在同一事务中保存设置、执行完整计划校验并置为 `active`。归档继续走现有独立入口。

这比增加“先 PUT、再 POST publish”两次请求更能避免设置已保存但发布失败的中间状态，也比继续接受任意 `status` 更清楚地约束允许的转换。运行中计划点击保存草稿会明确暂停新月份录入；界面必须在提交前后说明这一结果。

### 2. 100 元默认值在整数分层表示为 10,000

计划创建路径和数据库模型默认值统一改为 `10_000` 分，前端继续通过元/分格式化展示为 `100`。现有行不迁移，避免把用户已选的 1 元或其他取整单位误判为旧默认并覆盖。

仅修改前端初始值无法保证 API 或其他客户端创建的一致性，因此后端创建路径是权威默认；数据库默认同步更新用于防御绕过应用层的插入。

### 3. 现金承接余额与建议总额零头，未启用现金时保留最大余数法

领域计算按以下顺序执行：先精确计算建议总额；若存在规范名称精确为“现金”（比较前去除首尾空白）的启用标的，则每个非现金启用标的按其理论份额和计划单位向下取整，现金金额等于精确建议总额减去所有非现金金额。因此现金同时承接配置尾差、分项尾差与不足一个取整单位的建议总额零头。由于启用标的名称在计划内唯一，最多只能有一个现金承接项。

没有启用现金时继续先将建议总额按计划单位向下取整，再使用当前最大余数法，以保证所有非现金分项保持取整单位且不改变既有无现金计划的确定性。相比为数据库增加目的地类型列，使用已有规范名称无需数据迁移，并与当前预设模型一致；代价是将“现金”保留为具有领域语义的名称。

### 4. UI 使用两个提交动作共享同一份编辑数据

设置页保留一个表单状态，但提供“保存草稿”和“发布计划”两个按钮。两者提交相同设置和不同生命周期动作；发布按钮在客户端已知配置不完整时禁用并展示差额，但服务端仍重复全部校验。提交期间两个按钮都禁用，成功反馈明确区分“尚未开始”和“已开始”。发布成功后月度入口开放；草稿只允许查看概览、设置和历史只读内容。

### 5. 未开始计划使用受保护的独立永久删除命令

“未开始”在删除规则中定义为计划当前状态为 `draft` 且不存在任何月度记录。后端提供独立的草稿删除命令（例如 `DELETE /plans/:planID/draft?version=<version>`），保留现有 `DELETE /plans/:planID` 的归档语义，避免旧客户端把归档请求意外升级为永久删除。

删除命令在单个数据库事务中锁定或按版本匹配当前用户的计划，重新检查状态和月度记录是否存在，再删除计划所属的投资标的和计划本身。任何条件不满足、版本冲突或并发产生月度记录时均不删除任何数据。相比只在前端按 `status` 判断，这能防止伪造请求或陈旧页面永久删除已经开始的计划；相比增加“曾发布”字段，`draft` 加无月度记录准确覆盖本次确认的业务边界且无需迁移。

计划列表响应提供服务端计算的 `deletable` 标记，列表卡片只在可删除时展示“删除草稿”危险操作。用户必须在确认对话框中确认不可恢复的结果；删除成功后从列表移除该计划。运行中、已归档或有历史的计划继续使用归档能力，不显示永久删除入口。

### 6. 收入输入接受安全的加减算式

月度“上月总收入”字段从数字输入改为受限文本输入，仅接受非负金额、加号和减号，例如 `20000+500-100`。前端在预览和提交前使用同一个非 `eval` 解析器换算为分；格式不合法或结果为负时阻止提交并提示修正。保存的月度快照仍只存最终金额，不保存算式文本。

输入有效金额或算式时，字段下方实时显示格式化后的当前合计，提交负载直接使用该解析结果，避免普通数字转换把算式误写为 0。

### 7. 破坏性集成测试只允许专用测试库

集成测试在迁移后会清空业务表，因此测试启动必须解析 `MYSQL_TEST_DSN` 的数据库名，并在任何连接、迁移或清表之前拒绝名称不以 `_test` 结尾的数据库。文档示例使用独立的 `invest_planner_test`，开发库和用户数据不得作为测试目标。

## Risks / Trade-offs

- [名称“现金”承担特殊语义，重命名后不再承接尾差] → 在预设和结果说明中固定使用规范名称，并用领域测试覆盖启用、停用和缺少现金三种情况。
- [运行中计划保存草稿会暂停后续月度操作，可能令用户意外] → 按钮和确认反馈明确写出“保存后转为草稿/暂停”，运行中状态下强化提示。
- [数据库默认值与应用默认值漂移] → 同一改动更新两处常量，并增加创建计划的 API/仓储测试断言 10,000 分。
- [现金金额可能高于其理论比例] → 结果说明显示现金包含分项取整尾差和零头；算法保证现金非负且总额守恒。
- [并发编辑覆盖状态] → 延续现有版本号乐观锁，动作请求必须携带当前版本，冲突时不改变计划。
- [永久删除不可恢复] → 仅允许 `draft` 且无月度记录的计划，使用独立端点、服务端事务复核、版本匹配和明确的危险确认。
- [删除资格在页面打开后发生变化] → `deletable` 只用于界面提示，执行删除时始终重新查询状态与月度记录，冲突时保留全部数据并要求刷新。
- [集成测试误连开发库导致数据丢失] → 清表前强制校验数据库名以 `_test` 结尾，并提供专用测试库示例；普通验证不再把开发库 DSN 传给集成测试。

## Migration Plan

1. 先部署兼容新生命周期动作的后端及领域计算测试，再部署使用双按钮的新前端。
2. 更新创建默认值和数据库模型默认声明；不执行已有数据回填。
3. 用新建计划验证取整单位为 10,000 分，并分别验证保存草稿、发布、删除无历史草稿、拒绝删除运行中或有历史计划、现金承接尾差及无现金回退。
4. 回滚时恢复旧前后端行为；新建计划保存的 100 元取整值仍是合法自定义值，无需数据回滚。已生成月份继续按快照展示。

## Open Questions

无。默认取整单位按人民币 100 元解释；“现金”作为已启用规范标的时自动承接尾差。
